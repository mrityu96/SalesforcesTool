    This guide takes a CML (Constraint Modeling Language) model from a source org, where it was built and tested, to a target org. It also moves the Product associations (ExpressionSetConstraintObj rows) that link the model to products. Follow the steps in order the first time; later you can jump straight to the step you need.
    
              
    Order matters. CML refers to Context Definition tags and mappings. A CML deployment does not deploy Context Definition tags or mappings, so if the target org does not have them yet, deploy the Context Definition first. See the .

    1
    Read-only
    Before you start
    
                
    Install two things once, log in to your orgs, and start the tool.
    
              
      
                
    1. Python 3.9 or newer. macOS already has it (or run xcode-select --install). On Windows, install it from python.org and tick Add Python to PATH.
      2. 
                
    2. Salesforce CLI. Install it once with npm install -g @salesforce/cli.
      3. 
                
    3. Log in to every org you will use, giving each one a short alias:
                  
      sf org login web --alias Dev_Sandbox --instance-url https://test.salesforce.com
sf org login web --alias Release_QA  --instance-url https://test.salesforce.com
      
                  Use https://login.salesforce.com for production and Developer Edition orgs. The alias is what you will type to confirm every write.
      4. 
                
    4. Start the tool. Open the Start Tool Here folder and double-click the launcher for your computer: Open CML Tool for macOS.command, Open CML Tool for Windows.bat, or Open CML Tool for Linux.sh. Your browser opens at http://127.0.0.1:8787.
      5. 
                
    5. Stop the tool on macOS with Stop CML Tool for macOS.command. On Windows and Linux, close the launcher window.
      6. 
              
    
              
    Where does my data go? The tool runs only on your computer (127.0.0.1). It talks to Salesforce through your own Salesforce CLI login. There is no cloud service and no telemetry.
    
              
    Check before moving on: run sf org list in a terminal. Every org you need is listed and shows as Connected.
    
            
    

            
    
              
    2
    Read-only
    Find your way around the tool
    
                
    Learn the parts of the screen you will use in every step.
    
              
              
      
                
    1. Header tabs (the pill in the middle) switch between the six workspaces: Fetch & Deploy CML, Constraint Data, Compare CML, Context Definition Fix, XML Tools, and Help Me. On a smaller screen, some tabs move into More.
      2. 
                
    2. Runs locally (the green dot at the top right) shows that the tool is connected to its local server. Hover over it to see the version and build.
      3. 
                
    3. Shortcuts lists the keyboard shortcuts. The sun/moon switch changes between day and night mode.
      4. 
                
    4. Source org (left card) is where you read CML from. Target org (right card) is what you compare with. Both cards stay at the top of every tab that needs them.
      5. 
                
    5. Status messages appear under each action. Green means success, red means a problem, and blue is information.
      6. 
              
    
              
              
    Two badges tell you what an action does. Read-only steps only read from Salesforce. Writes Salesforce steps change an org, and each one asks you to type the org alias before it runs.
    
              
    A yellow banner at the top means the tool's files changed while it was running. Restart means stop and start the tool again. Reload the page means refresh the browser tab.
    
            
    

            
    
              
    3
    Read-only
    Choose the source org and exact CML version
    
                
    Tell the tool exactly which CML version you want to move.
    
              
              
      
                
    1. In the Source org card, open Source org and pick the org alias (for example Dev_Sandbox).
      2. 
                
    2. Check the tinted box at the top right of the card. Org ID confirms you picked the right org; click it to copy. Salesforce Release shows the release the org runs, for example 262.14.26 · Summer '26 Patch 14.26.
      3. 
                
    3. Open Source CML exact version. The tool lists every CML model in the org and every version of each model. Type in the search box to narrow the list.
      4. 
                
    4. Pick the exact version. The pill shows its runtime status: ● ACTIVE or ○ INACTIVE.
      5. 
              
    
              
              
    Do not assume the newest version is the right one. An org can have several versions of the same model, and only one is active at runtime. Ask the model owner which version to move if you are unsure.
    
              
    Check before moving on: the Org ID, model name, version number, and status pill match what you expect.
    
            
    

            
    
              
    4
    Read-only
    Fetch the CML
    
                
    Load the exact source CML into the editor so you can read it.
    
              
      
                
    1. Open the Fetch & Deploy CML tab.
      2. 
                
    2. Click Fetch CML beside the CML Editor heading.
      3. 
                
    3. The CML appears in the editor with line numbers and colour highlighting. The tool also saves a copy on your computer, and the status message shows where.
      4. 
                
    4. The badge beside CML CONTENT says Not modified. It changes as soon as you edit, so you always know whether the editor still matches Salesforce.
      5. 
                
    5. Use Copy to copy everything, or Download .cml to save the file, for example to attach it to a review.
      6. 
              
    
              
              
    Unsaved work is protected. If you edit and then accidentally reload the page, the tool offers Restore draft when you pick the same org, model, and version again in that tab. The draft stays only in that browser tab, and a fresh fetch or a successful deploy clears it.
    
              
    Check before moving on: the editor is not empty, and the first lines are the model you expected.
    
            
    

            
    
              
    5
    Read-only
    Search and edit in the editor
    
                
    Find types, attributes, and constraints quickly, and make small edits safely.
    
              
      
                
    1. Click inside the editor and press Cmd+F (macOS) or Ctrl+F (Windows/Linux). A search bar opens at the bottom of the editor.
      2. 
                
    2. Type what you are looking for, for example monthlyPrice. Every match is highlighted. Use next, previous, or all to move between them.
      3. 
                
    3. Tick match case, regexp, or by word to narrow the search.
      4. 
                
    4. Use replace or replace all to change text in place.
      5. 
                
    5. Press Cmd/Ctrl+/, or click // Line comment, to comment out the selected lines. /* */ Block comment wraps a whole selection.
      6. 
                
    6. Press Esc to close the search bar.
      7. 
              
    
              
              
    Editing here does not change Salesforce. Nothing is written until you deploy in step 9.
    
            
    

            
    
              
    6
    Read-only
    Check best practices
    
                
    Catch common CML mistakes before they reach another org.
    
              
      
                
    1. In the editor toolbar, click Check best practices.
      2. 
                
    2. A report opens under the editor with a quality score and a list of findings. The same findings are underlined on the affected lines in the editor; hover an underline to read it.
      3. 
                
    3. Each finding names the rule, explains the problem in plain language, and points to its line.
      4. 
                
    4. Where a fix exists, a Before → After example shows the corrected CML. Read it, then use Copy and paste the correction into the editor yourself.
      5. 
                
    5. Click Hide best practices to clear the report and the underlines. Run the check again after editing.
      6. 
              
    
              
              
    The score is guidance. A high score does not prove Salesforce will compile or activate the CML. Activation in Salesforce (step 10) is the real test.
    
            
    

            
    
              
    7
    Read-only
    Compare source and target CML
    
                
    See exactly what will change in the target org, and build the final version there.
    
              
      
                
    1. In the Target org card, pick the target org (for example Release_QA) and its exact version. Check its Org ID, release, and status pill as you did for the source.
      2. 
                
    2. Open the Compare CML tab and click Compare source ↔ target. The source is on the left and the target is on the right. The two panes scroll together.
      3. 
                
    3. Read the colours and markers: ~ purple means the line changed, − orange means it is only in the source, and + blue means it is only in the target. The summary above the panes counts each kind.
      4. 
                
    4. Tick Semantic summary to compare by meaning instead of by line. It ignores formatting, comments, and moved blocks, and marks whole types as MODIFIED, ADDED, or REMOVED. Tick Show only differences to hide matching lines.
      5. 
                
    5. Click a → arrow between the panes to copy one change into the target draft, or click Merge all → to copy every change. Each applied change gets a ← arrow that undoes just that change.
      6. 
                
    6. Click Edit target to type directly in the target draft, then Save edits. Reset target draft puts back the target exactly as it was fetched.
      7. 
                
    7. When the draft is right, click Review & Deploy target draft. The tool loads the draft into the Fetch & Deploy editor and pre-selects the target org for step 8.
      8. 
              
    
              
              
    Merging only changes the draft in your browser. The banner above the panes reminds you that Salesforce has not been changed yet.
    
              
    Check before moving on: every difference left in the comparison is one you meant to keep.
    
            
    

            
    
              
    8
    Read-only
    Check the target version status
    
                
    Make sure the exact target version can be written to.
    
              
      
                
    1. On the Fetch & Deploy CML tab, scroll below the editor to the deployment panel.
      2. 
                
    2. Pick Deploy to org. It always starts empty, so you must choose the target on purpose.
      3. 
                
    3. Pick Target exact CML version, the version you will overwrite.
      4. 
                
    4. Click Check target status. The Target version status panel shows whether that exact version is Active or Inactive and whether it can be deployed to.
      5. 
                
    5. If the version is Active, deployment is blocked, because overwriting a live model would change runtime behaviour immediately. Deactivate it in Salesforce, or use Deactivate CML here (it asks you to type the alias), or pick an inactive version.
      6. 
              
    
              
            
    

            
    
              
    9
    Writes Salesforce
    Deploy the CML
    
                
    Write the reviewed CML to the exact target version, with a backup and a verification.
    
              
      
                
    1. Read the editor one last time. Whatever is in the editor is exactly what will be deployed.
      2. 
                
    2. Click Deploy CML. The tool checks the target status again on the server.
      3. 
                
    3. A confirmation window shows the model, target org, and exact version. Type the target org alias exactly (for example Release_QA). The Deploy CML button stays disabled until it matches. Press Esc to cancel.
      4. 
                
    4. The tool then:
                  
        
                    
      • saves a backup of the current target CML on your computer,
        • 
                    
      • writes the new CML,
        • 
                    
      • reads it back from Salesforce and compares a fingerprint (SHA-256) to prove it was saved exactly, and
        • 
                    
      • if that check fails, restores the backup automatically and tells you.
        • 
                  
      5. 
                
    5. The status message lists the backup file and the deployment report file. Keep them until you have tested the target org.
      6. 
              
    
              
              
              
    Deploying does not activate the CML. The new version stays inactive until you activate it in step 10.
    
            
    

            
    
              
    10
    Writes Salesforce
    Activate and test in Salesforce
    
                
    Let Salesforce compile and validate the CML, then prove it works.
    
              
      
                
    1. Open the target org in Salesforce and go to Constraint Builder for the model.
      2. 
                
    2. Activate the exact version you deployed. Salesforce compiles the CML and reports any errors, for example an association that points to a type the CML no longer has.
      3. 
                
    3. If activation fails, read the error, fix the CML in the source (or in the editor), and repeat steps 7–9.
      4. 
                
    4. After activation, configure a few real products in the target org to confirm the rules behave as expected.
      5. 
              
    
              
    Why the tool does not activate for you. Activating by setting IsActive directly would skip Salesforce's compiler and validation. The tool blocks that on purpose and leaves activation to Constraint Builder.
    
            
    

            
    
              
    11
    Writes Salesforce
    Deploy Product associations
    
                
    Copy the rows that link CML types to products, which a CML deployment does not create. This is the Constraint Data Deploy workflow.
    
              
      
                
    1. Open the Constraint Data tab. Keep the same source and target orgs and exact versions selected.
      2. 
                
    2. In Match records by (foreign key field), choose a field that has the same value in both orgs, for example Global_Key__c. Record Ids differ between orgs, so they cannot be used. Prefer a unique external Id; Name only works when names are unique.
      3. 
                
    3. Optional: click View Source Org Data to list the source rows only.
      4. 
                
    4. Click Compare data. The summary shows the Source pills on the left (rows, only in source), the Target pills on the right (rows, only in target), and the Comparison pills underneath (matched, blocked, need review, CML definition differences).
      5. 
                
    5. Read the Status column. Matched rows are already in the target. Add to target rows can be deployed. Only in target rows can be deleted. Blocked rows list the reason as bullets, for example a classification attribute missing in the target catalog.
      6. 
                
    6. Use Show, the search box, and Copy for Excel to filter the table or share it with another team.
      7. 
                
    7. Additions are ticked by default; deletions are never ticked by default. Use Select all adds, Clear adds, Select all deletes, and Clear deletes to change the selection. The bar shows how many rows you will add and delete.
      8. 
                
    8. Click Deploy selected to target and type the target alias to confirm. The server re-checks catalog dependencies before writing.
      9. 
                
    9. Read Deployment results. Every row shows ✓ or ✗; a blocked row lists each missing item as a bullet.
      10. 
              
    
              
              
              
    The tool never creates catalog data. Products, classifications, attributes, and relationships must be deployed through their normal process. Fix what a blocked row lists, then click Compare data again.
    
              
    Deletions are permanent. The tool archives each deleted row first, so you can restore it in step 12.
    
            
    

            
    
              
    12
    Writes Salesforce
    Recover if something goes wrong
    
                
    Undo a CML deployment or restore deleted associations.
    
              
      
                
    1. Restore a CML backup: in the deployment panel, pick the target org and exact version, choose a file in Recovery backup, and click Restore Backup CML. The tool first saves another backup, so the restore can itself be undone.
      2. 
                
    2. Restore deleted associations: on the Constraint Data tab, choose a file in Deletion archive and click Restore archive. Use Download archive to keep a copy.
      3. 
                
    3. Download a deployment report from the Deployment report list to share exactly what was changed.
      4. 
                
    4. If a result says Partial deployment — recovery required, some changes were saved and some were not. Read every row before retrying.
      5. 
              
    
              
    Every restore asks you to type the target alias, like every other write.

    Troubleshooting
    
                
    Quick answers to common problems.
    
              
    
                
    My org is not in the list.
    Run sf org list. If the org is missing or shows as expired, log in again with sf org login web --alias YourAlias, then reopen the org list. The tool reads your Salesforce CLI logins.
    
                
    “Session expired” or an authentication error.
    Your CLI login expired. Run sf org login web --alias YourAlias again; no restart is needed.
    
                
    Deploy says the target version is Active.
    The tool never overwrites an active version. Deactivate it (step 8) or choose an inactive version.
    
                
    A yellow banner says “Restart”.
    The tool's files changed while it was running. Stop and start the tool.
    
                
    A yellow banner says “Reload the page”.
    Refresh the browser tab.
    
                
    Association rows are blocked.
    The target catalog is missing what the bullets list. Deploy that catalog data, then click Compare data again.
    
                
    Windows: [WinError 2] when loading orgs.
    Start the tool with Open CML Tool for Windows.bat, and make sure sf works in a new Command Prompt.
    
              
    
            
    
          
    

          
          
    
            
    
              
    A Context Definition tells Salesforce where each CML attribute gets its data (for example, which Order field fills Channel__c). When you add attributes in a source org, the target org needs the same tags and mappings before the CML can work there. This guide copies those additions into the target org's Context Definition without removing anything the target already has.
    
              
    Two words used throughout: Base is the Context Definition from the org you will deploy to (the target). Modified is the one that has the changes you want (the source).

    1
    Read-only
    Understand what this does
    
                
    Know the rules the tool follows, so the results make sense.
    
              
      
                
    • It adds and updates; it never deletes. Anything that is only in Base stays in Base.
      • 
                
    • It reads orgs but never deploys. Retrieving is read-only. At the end, the tool gives you a file and the exact sf commands, and you run them yourself.
      • 
                
    • It respects Salesforce's limits. Salesforce does not allow changing an existing attribute's data type, field type, key, or transient flag. The tool leaves those out and lists them as Not applied.
      • 
                
    • It knows about Salesforce releases. Standard elements come from SalesTransactionContext__stdctx, and each org inherits a version of it (for example 67.11 or 68.26). Standard elements that exist only in a newer release are marked Salesforce release and left unticked, because the target gets them automatically when its org is upgraded.
      • 
                
    • It fixes org-specific Ids. Record Ids inside hydration settings differ per org, so the build rewrites them to portable names.
      • 
              
    
            
    

            
    
              
    2
    Read-only
    Choose the source and target orgs
    
                
    Point the tool at the org with the changes and the org you will deploy to.
    
              
      
                
    1. Open the Context Definition Fix tab. The org cards stay at the top; CML versions are hidden because they are not needed here.
      2. 
                
    2. In Source org, pick the org that has the new tags and mappings. It becomes Modified.
      3. 
                
    3. In Target org, pick the org you will deploy to. It becomes Base.
      4. 
                
    4. Compare the two Salesforce Release values. If the source runs a newer release, expect some items to be marked Salesforce release later.
      5.

    Read-only
    Retrieve Base and Modified
    
                
    Load both Context Definitions into the editors.
    
              
      
                
    1. In the Base pane, choose the Context Definition name, for example SalesTransactionContextExt. If the list looks old, click Refresh.
      2. 
                
    2. Click Retrieve. The XML appears in the editor, and the badge under the name changes from Empty to Retrieved, showing the org and time.
      3. 
                
    3. Do the same in the Modified pane. Choose the same Context Definition name.
      4. 
                
    4. Check the footer of each pane: the line count and Valid XML. Invalid XML means the content is damaged; retrieve it again.
      5. 
                
    5. Alternatively, paste XML with Paste. The tool then does not know which org it came from, and later steps warn you about that.
      6. 
                
    6. Press Cmd/Ctrl+F inside an editor to search, just like the CML editor. Even very large files (30,000+ lines) stay responsive.
      7. 
                
    7. Click Analyze differences, the large button under the editors.
      8. 
              
    
              
              
    If you edit the XML by hand, the badge changes to Edited, so you can see that the content no longer matches the org.
    
            
    

            
    
              
    4
    Read-only
    Analyze the differences
    
                
    Understand what Modified has that Base does not.
    
              
      
                
    1. After you click Analyze differences, the page scrolls to step 2. The green summary says how many additions and value changes were found, how many are Salesforce release content, and how many are not applied.
      2. 
                
    2. The middle rail between the editors shows Total changes, Added, Updated, and Base only.
      3. 
                
    3. Why are the line counts different? explains the gap. Salesforce writes some elements differently, so line counts alone can mislead. The tabs list Present only in Base, Present only in Modified, Materially changed, and Element counts.
      4. 
              
    
              
            
    

            
    
              
    5
    Read-only
    Review what will not be applied
    
                
    Know in advance which differences will stay as they are in Base.
    
              
      
                
    1. Open Not applied.
      2. 
                
    2. Schema change rows are attribute changes Salesforce does not allow on an existing attribute (data type, field type, key, transient). Base keeps its current value.
      3. 
                
    3. Only in Base rows are items Modified no longer has. Base keeps them, because the tool never deletes.
      4. 
                
    4. If one of these changes really must happen in the target, plan it separately: for example, remove the old attribute in Salesforce first, and then run this guide again.
      5. 
              
    
              
            
    

            
    
              
    6
    Read-only
    Select the changes to include
    
                
    Tick exactly the additions and value changes you want in the target.
    
              
      
                
    1. The counters at the top show Total changes, Context Mappings, Context Attributes, and Required Parent Blocks.
      2. 
                
    2. Search by field or mapping name, or filter with the chips: Ready, Required Parent Blocks, Value changes, Context Mappings, Context Attributes, and Selected.
      3. 
                
    3. Each group (for example Region__c) contains its mapping and attribute. Click a row to see its Revenue Cloud path and an XML preview on the right.
      4. 
                
    4. Tick or untick items. Select all, Deselect all, Expand all, and Collapse all help with long lists. The bottom line shows Total and Selected.
      5. 
                
    5. Items marked Salesforce release start unticked. Leave them unticked unless the target org already runs that release. If you tick a mapping that needs one of them, the build adds that item too and warns you in step 7 and step 8.
      6. 
                
    6. When a mapping needs a parent block that Base does not have, the tool adds the complete Required Parent Block for you.
      7. 
              
    
              
              
    Leave out test or experimental fields that exist only in the source org. They would fail the field check in step 8.
    
            
    

            
    
              
    7
    Read-only
    Build the Context Definition
    
                
    Create the patched Context Definition: Base plus your selected changes.
    
              
      
                
    1. In step 3, click Build Context Definition.
      2. 
                
    2. The Patched result pane shows the new XML. It is read-only; use Copy or Download.
      3. 
                
    3. The Apply report counts Added, Updated, Skipped, and Errors, and lists every change. View raw report shows the full text report.
      4. 
                
    4. If the report says Ids were normalized, the tool replaced org-specific record Ids with portable names. That is expected.
      5. 
              
    
              
              
    Check before moving on: Errors is 0, and the added and updated counts match what you selected.
    
            
    

            
    
              
    8
    Read-only
    Check fields in the target org
    
                
    Prove that every field the new mappings read exists in the org you will deploy to.
    
              
      
                
    1. In step 4, choose Org you plan to deploy to. The box next to it shows where Base and Modified came from.
      2. 
                
    2. Read any warnings, for example when the chosen org is not the org Base was retrieved from, or when the build includes Salesforce release content.
      3. 
                
    3. Click Check fields in this org (read-only). The tool checks every object and field the mappings read, using the org's newest API version so recent fields are not missed.
      4. 
                
    4. Each problem is labelled added by this build or already in Base.
                  
        
                    
      • Added by this build will likely make the deploy fail. Either deploy the missing field first, or untick that item in step 6 and build again.
        • 
                    
      • Already in Base was already in the target's Context Definition before this build. It is usually a standard mapping for a feature the org does not use, and it does not block the deploy.
        • 
                  
      5. 
              
    
              
            
    

            
    
              
    9
    Writes Salesforce
    Deploy with the generated commands
    
                
    Deploy the patched Context Definition yourself, check-only first.
    
              
      
                
    1. Click Download deployable file and save it at the path shown, for example force-app/main/default/contextDefinitions/SalesTransactionContextExt.contextDefinition-meta.xml, in your SFDX project.
      2. 
                
    2. Click Download package.xml and save it at the path shown, for example manifest/contextDefinition-package.xml.
      3. 
                
    3. In a terminal, from the project folder, run the check-only command. It validates without changing the org:
                  
      sf project deploy start --manifest manifest/contextDefinition-package.xml --target-org Release_QA --wait 30 --dry-run
      4. 
                
    4. Only if the check succeeds, run the real deploy, which is the same command without --dry-run. Use the Copy buttons next to each command.
      5. 
              
    
              
              
    Follow your team's approvals. For UAT and production orgs, get the required approval before running the real deploy.
    
            
    

            
    
              
    10
    Read-only
    Verify, then deploy the CML
    
                
    Confirm the target now has the changes, then continue with the CML.
    
              
      
                
    1. Back in step 1, click Retrieve in the Base pane again to load the target's new Context Definition.
      2. 
                
    2. Click Analyze differences. The items you deployed should be gone. Only Base only, Not applied, and unticked Salesforce release items should remain.
      3. 
                
    3. Continue with the  to move the CML and its Product associations.
      4. 
              
    
            
    

            
    
              
    11
    Read-only
    Troubleshooting
    
                
    Quick answers to common problems.
    
              
    
                
    The check-only deploy fails with a missing field.
    Run step 8 again; it shows which mapping reads that field. Deploy the field first, or untick the item and build again.
    
                
    The field check reports many “already in Base” problems.
    These are usually standard mappings for features the org does not use (for example multi-currency or Sales Agreements). They were already accepted in that org and do not block your deploy.
    
                
    A change I need is under “Not applied”.
    Salesforce does not allow that change on an existing attribute. Remove or rename the attribute in the target first, then build again.
    
                
    Step 4 warns that Base was pasted.
    The tool cannot confirm which org the XML came from. Retrieve Base from the target org instead, so the checks match the org you deploy to.
    
                
    The Retrieve list is empty.
    Click Refresh. If it is still empty, check your CLI login for that org with sf org list.
